# 주석 덜어내기

이 스킬은 새 주석을 다는 게 아니라 이미 있는 주석을 줄이는 일만 한다. 기본값은 지우기이고 남길 이유가 분명한 주석만 남긴다.

## 1. 범위 정하기

사용자가 지정한 대상은 다음과 같다. 비어 있으면 지정하지 않은 것이다.

> $ARGUMENTS

스킬을 불렀을 때의 저장소 상태는 다음과 같다. 저장소가 아니면 비어 있다.

- 현재 브랜치: !`git branch --show-current 2>/dev/null || true`
- 원격 기본 브랜치: !`git rev-parse --abbrev-ref origin/HEAD 2>/dev/null || true`
- 커밋되지 않은 변경:

```!
git status --short 2>/dev/null || true
```

### 어떤 파일을 보나

대상은 인자로 받을 수도 있고 요청 문장에 들어 있을 수도 있다. 둘 다 보고 아래에서 고른다.

- 파일이나 폴더를 지정하면 그 안의 파일을 본다.
- "이번 브랜치", "이 브랜치에서 작업한" 처럼 브랜치를 말하면 기본 브랜치에서 갈라진 뒤 바뀐 파일을 본다. `git diff --name-only <기본 브랜치>...HEAD`에 커밋되지 않은 변경을 더한다. 기본 브랜치는 위의 원격 기본 브랜치를 쓰고 비어 있으면 main이나 master 중 있는 것을 쓴다. 둘 다 없으면 사용자에게 묻는다.
- "이번 커밋", "마지막 커밋" 이라고 하면 HEAD 커밋 하나를 본다. 커밋 해시를 주면 그 커밋을, "최근 3개 커밋" 처럼 개수를 말하면 `HEAD~3..HEAD`를 본다. 파일 목록은 `git show --name-only` 나 `git diff --name-only`로 얻는다.
- 아무것도 지정하지 않으면 커밋되지 않은 변경을 보고 그것도 없으면 이번 브랜치를 본다. 둘 다 비어 있으면 어디를 정리할지 사용자에게 묻는다.
- 지워진 파일은 건너뛴다.

### 파일 안에서 어디까지 보나

- 기본은 바뀐 줄에 있는 주석만 다룬다. 범위에 맞는 `git diff`에서 추가되거나 바뀐 주석만 고르고 손대지 않은 기존 주석은 그대로 둔다.
- "파일 전부", "작업한 파일 전부", "파일 통째로" 처럼 파일 단위로 말하거나 파일과 폴더를 직접 지정하면 그 파일의 주석 전체를 본다.
- 어느 쪽인지 애매하면 시작하기 전에 짧게 묻는다.

### 공통

- 범위를 정했으면 수정하기 전에 대상 파일 수와 어느 쪽 깊이로 보는지 한 줄로 알린다.
- 주석만 고친다. 코드 동작, 이름, 구조는 건드리지 않는다. 고칠 만한 코드가 보이면 끝에 제안으로만 남긴다.

## 2. 지울 주석

### 변경 이력과 작업 메모

코드가 아니라 작업 과정을 설명하는 주석. 이력은 git에 있으니 전부 지운다.

- `기존 X에서 Y로 변경`, `~ 때문에 수정함`, `FIX:`, `NEW:`, `Updated to ...`
- `이제 ~를 지원한다`, `더 이상 ~를 쓰지 않는다`
- `Step 3`, `임시. 나중에 정리`, `TODO: 리팩터링` 처럼 담당이나 이슈 없이 남은 진행 메모
- 지운 코드를 설명하는 주석이나 주석 처리된 옛 코드

### 코드를 다시 말하는 주석

- 다음 줄을 문장으로 옮긴 것. 사용자 목록을 가져오는 호출 위에 붙은 "사용자 목록을 가져온다"
- 다음 줄들을 번호로 나눈 단계 주석. `1. 검증`, `2. 저장`
- 함수 이름과 시그니처를 그대로 풀어 쓴 doc comment. 이 경우 doc comment를 지우지 말고 이름이 말하지 않는 것만 남기거나 한 줄 요약으로 줄인다.
- 블록 끝을 알리는 `end if`, 섹션을 나누는 `===== helpers =====`

### 과한 설명

- 언어 문법이나 표준 라이브러리 사용법을 가르치는 설명, 다른 언어나 프레임워크에 빗댄 설명
- 프레임워크가 어떻게 동작하는지 풀어 쓴 설명
- 한 가지 이유를 말하려고 여러 줄을 쓴 주석. 이유 한 문장만 남긴다.
- 같은 내용을 doc comment와 본문 주석에서 두 번 말하는 경우. 한 곳만 남긴다.

## 3. 다시 쓸 주석

남길 내용은 있지만 읽기 어려운 주석은 내용을 지키면서 짧은 평범한 문장으로 고친다.

- 화살표(`→` `←`), 가운뎃점(`·`), 트리 그림(`├─`)으로 이은 주석은 문장으로 푼다.
- `라벨:` 형태의 콜론 라벨, `(0부터)` 같은 괄호 덧붙임은 문장 안에 녹이거나 뺀다.
- 쉼표로 길게 이은 문장은 두 문장으로 나누거나 줄인다.
- 굵게, 이모지, 과한 강조(`IMPORTANT`, `NOTE`, `!!!`)는 뺀다. 정말 중요한 경고라면 무엇이 왜 위험한지 한 문장으로 쓴다.
- 고칠 때 형식은 그 언어의 문서화 주석 관례와 저장소에 자리 잡은 스타일을 따른다. 주석 언어도 저장소에서 쓰는 언어를 따른다.

## 4. 남길 주석

아래는 코드만으로 알 수 없으므로 남긴다.

- 왜 이렇게 했는지. 다른 방법을 쓰지 않은 이유
- 외부 시스템이나 라이브러리 버그를 우회하는 코드의 설명
- 비직관적인 비즈니스 규칙이나 도메인 규칙
- 순서를 바꾸면 깨지는 코드, 지우면 안 되는 것처럼 보이지 않는 코드에 대한 경고
- 공개 API의 doc comment. 언어 관례상 필요한 doc comment는 지우지 말고 짧게 줄인다.
- 린터나 컴파일러, 빌드 도구가 읽는 지시 주석

## 5. 진행 방법

1. 범위 안의 주석을 모두 훑고 지우기, 다시 쓰기, 남기기로 나눈다.
2. 확실한 것은 바로 고친다. 변경 이력, 코드를 다시 말하는 주석, 기초 설명이 여기에 들어간다.
3. 지울지 애매한 주석은 고치지 말고 파일 위치와 함께 목록으로 보여 준 뒤 사용자에게 묻는다. 이유를 담고 있을 수도 있는 주석이 여기에 들어간다.
4. 주석을 지워서 생긴 빈 줄이 겹치면 정리한다. 그 밖의 서식은 건드리지 않는다.
5. 끝나면 지운 개수와 고친 개수, 확인이 필요한 목록을 짧게 알린다.
