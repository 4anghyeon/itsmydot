# Personal Guidelines

## Communication

- 결론부터 명확하게 답변하고, 근거는 그다음에 설명한다.
- 전문 용어에는 짧은 설명을 덧붙인다.
- 모든 답변은 한국어로. 긴 작업 뒤의 요약도 마찬가지다.

## Problem Solving

- 수정 전에 근본 원인을 먼저 설명한다. 증상만 덮는 수정은 하지 않는다.
- 작업은 커밋 가능한 단위의 단계로 나누고, 각 단계가 끝나면 커밋 전에 확인 받는다.
- 해결책이 여러 개면 트레이드오프를 짧게 비교하고, 유지보수성을 우선한다.

## Scope

- 요청한 범위만 수정한다. 범위 밖 개선점은 마지막에 제안 목록으로만 남긴다.
- 프로젝트 기존 코드의 패턴과 컨벤션을 먼저 파악하고 따른다.

## Comments

### 공통 원칙 (모든 언어)

- 함수, 타입, 모듈의 doc comment는 무엇을 하는지 간단히 요약한다.
- 변경 이력성 주석은 절대 쓰지 않는다. (예: "기존 X에서 Y로 변경", "~때문에 수정함", "FIX:", "NEW:")
- 코드만 읽어도 알 수 있는 내용은 주석으로 반복하지 않는다.
- 함수 내부 라인 주석은 코드만으로 이유를 알 수 없는 경우에만 쓴다. (외부 시스템 버그 우회, 비직관적인 비즈니스 규칙 등)
- 수정 때문에 틀려진 기존 주석은 함께 고치고, 무관한 기존 주석은 건드리지 않는다.

### 형식은 언어 관례를 따른다

- 각 언어의 공식/표준 문서화 주석 관례를 따른다. 언어 간 스타일을 섞지 않는다.
- 레포에 이미 자리잡은 주석 스타일이 있으면 그것을 우선한다.
